# Reusable source-first textbook lesson-generation prompt

Use this prompt only after the selected official NCERT source-book extraction and visual-candidate workflows have succeeded. It applies to Classes 6–8 Science and Mathematics and must be scoped to the exact selected book, chapter and source hashes.

---

**Task:** Prepare source-bound, bilingual lesson content for QuantaEdge using only the verified source artifacts in this repository.

1. **Resume from repository evidence, not chat memory.** Read `docs/ai/textbook-extraction-execution.md`, this prompt, the relevant production index/coverage ledger, `data/structured-lessons/question-rendering-registry.v1.json`, and [Issue #56](https://github.com/Manav326/QuantaEdge/issues/56). Check current `main` and the latest applicable staged tree/blob pointers before editing. Never regenerate an existing artifact just because it is easier than resuming it.

2. **Lock the source identity.** Resolve the exact official NCERT whole-book PDF, edition/reprint, language, book ID and SHA-256 from the repository's current manifests. Use only the selected class and subject. Do not guess, substitute an edition, combine incompatible sources, or proceed while a required source/part is missing or ambiguous.

3. **Map the whole chapter before deciding lesson count.** Inspect extracted page text and rendered source pages in English and Hindi. Derive lesson/topic boundaries from actual numbered headings and coherent subsections; do not force a preset topic count. Record PDF page numbers separately from printed page numbers and keep every lesson linked to its canonical chapter/topic and source refs.

4. **Inventory the source before writing lessons.** The coverage ledger must enumerate, by stable ID, every relevant section/subsection, figure and panel, table/chart, numbered or unnumbered activity/experiment, worked example, sidebar/case, safety note, special box, key term/keyword, summary point, end-of-chapter question and “Learning further”/extension task in both language editions. Compare the inventory to the rendered PDFs. Do not represent a count-only note such as “9 activities” as item-level coverage: list the nine individual activities. Flag page-boundary, reading-order, OCR, translation or visual uncertainty explicitly.

5. **Map every inventoried item to an outcome.** Add a `source_inventory.items[]` record for each source item and a matching `coverage_map[]` record keyed by the same stable ID. Each mapping must either point to the exact lesson path plus content block, activity block or practice-question ID that covers it, or carry an explicit `REFERENCE_ONLY`, `EXCLUDED_WITH_REASON` or `PENDING_SOURCE_REVIEW` disposition with a reason. Unmapped, duplicate or invented references are errors. A source item can be taught in the explanation/activity and need not be converted into a question; coverage means it is accounted for, not that every item gets a quiz.

6. **Author the lesson, not a type quota.** Every lesson needs a meaningful Explain section and a Practice section appropriate to its objectives. The question-rendering registry is a catalogue of supported response contracts, **not a quota**. Choose a question type only when the concept, learner objective and source context justify it. Do not generate one of every type, do not rotate through types to balance counts, and do not pad a topic with redundant questions. Produce the smallest sufficient set that meaningfully assesses the distinct assessable objectives; a topic may have one type, several types, or no example of a particular type. The chapter may naturally use a varied mix, but diversity is a result of the content, not a fixed distribution.

7. **Keep types and system contracts compatible.** For structured lessons, use only supported `type` values and their exact `rendering_contract_id` from the structured lesson registry. Preserve the data contracts of the existing question bank separately: do not rename legacy types or map new structured types onto legacy ones just to pass validation. A numerical task should use numerical grading if that contract is available; short answers must remain pending review unless an explicit validated grader exists. Never invent answer keys, grading rules or supported UI behavior.

8. **Keep content chapter-specific and original.** Explain concepts in age-appropriate language without reproducing textbook prose or exercise questions verbatim. Do not turn a passing mention of another chapter into a mini-lesson. Every practice item must assess an objective and cite only source pages that support it. Calculate mathematics independently; do not invent science facts, safety instructions, units or missing context.

9. **Keep English and Hindi semantically paired.** Use identical stable lesson, objective, block, activity, question and option IDs across the paired content. Keep correct answers, grading, intended difficulty and objective links equivalent. Localize all visible prompts, options, diagram labels, alt text, captions, activities, controls, feedback, answer guides and rubrics. Do not use empty fields or silently fall back to the other language. Source-language parity requires semantic review, not merely two non-empty strings.

10. **Apply visual and publication gates.** Use only candidates tied to the exact source book/PDF hash/page. A candidate is not an approved student asset. Do not use an English whole-page screenshot in a Hindi lesson. Image-observation questions require an identified, relevant visual and remain blocked until the exact visual is rendered, rights/provenance-checked, translated as needed, accessibility-reviewed and approved. Keep generated data draft-only and `publication_allowed:false`.

11. **Validate coverage and contracts before checkpointing.** Run `scripts/validate_structured_lesson_coverage.py` on the coverage ledger and source inventory. Parse every artifact; validate stable IDs, bilingual fields, chosen question contracts, answer/option/matching/rubric references, lesson-path/block/question references, source book/PDF hashes, source-page references and coverage-map completeness. Structural success is not source completeness, scientific approval, bilingual approval or publishability. Record type counts as descriptive statistics only; never require equal counts or one of every type.

12. **Stage one chapter batch safely.** Add only the source-bound lesson data, source inventory/coverage map, coverage ledger, production index and resume notes needed for the chapter. Do not commit each topic or move a branch ref while the content batch is active. Update Issue #56 once after the complete chapter batch has been structurally validated, with lesson/topic list, observed counts by type, coverage-validator results, review blockers, exact staged tree/blob SHAs and next action. Commit only when the user explicitly asks to finalize the batch.

**Deliverable:** bilingual lesson artifacts; an item-level source inventory and coverage map; source references; descriptive question-type counts; validator output; a source/review report; and a resume-safe Issue #56 checkpoint. Keep human/source/science/translation/visual review blockers explicit.
