# TRE-4 assessment-course import and HRMS release

## Target course structure

- Source institution: QuantaEdge (`QUANTA-EDGE`)
- Course: `TRE-4 · Computer Science`
- Course type: `ASSESSMENT`
- Delivery mode: `ASSESSMENT_ONLY`
- Hierarchy: **Course → test packs → assessments/tests → ordered question snapshots**
- Test packs: one versioned pack each for TRE 1.0, TRE 2.0 and TRE 3.0

This is not a school-class course. The importer does not create or require a `curriculum_class`, `curriculum_subject`, or `curriculum_chapter` association. Exam sections (General Studies, Computer Science and qualifying language) stay as section metadata on the question snapshots rather than being represented as fake school subjects or chapters.

The complete-archive batch importer creates the source-owned course and its initial release itself; do not pre-create a class-bound TRE4 course before running it. If an existing TRE4 course is still class-bound, the importer refuses to rewrite it in place. Reconcile that existing draft through the course-version workflow before retrying. The importer never changes a reviewed release's content fingerprint.

## Source materials and question review

The source register is `data/TRE-Papres/source-register.json`; extracted question inventory is generated by `scripts/extract_tre_source_questions.py`. Source PDF hashes and exact question identities are checked before any database write.

The three papers have the following inventory:

- TRE 1.0: 120 questions; paper-specific negative-marking fraction of 0.25.
- TRE 2.0: 150 questions, including the qualifying-language section.
- TRE 3.0: 150 questions (30 qualifying-language + 40 General Studies + 80 Computer Science), preserving language IDs E-1 through E-8 and H-9 through H-30.
- General Studies and Computer Science are scored; qualifying-language questions are stored but excluded from the aggregate scored result.
- Shared passages/stimuli stay on their child question snapshots with a stable group ID.

No official answer key or explanation is guessed. Questions are imported with unresolved answer payloads and `PENDING_HUMAN_REVIEW` statuses. Import success is not content approval and does not make tests visible to learners.

## Inspect and import

Install the importer dependencies:

```powershell
python -m pip install "psycopg[binary]>=3.2,<4" pymupdf
```

From the repository root, first run the dry-run. It validates source counts, source identities and SHA-256 checks without database writes:

```powershell
python scripts/import_tre4_course.py --archive data/TRE-4_PYQ.zip
```

After reviewing the dry-run output and confirming the required migrations are applied, set the local API PostgreSQL URL in the current PowerShell session and apply:

```powershell
$env:TRE4_DATABASE_URL = "postgresql://quantaedge:YOUR_LOCAL_DB_PASSWORD@localhost:5432/quantaedge"
python scripts/import_tre4_course.py --archive data/TRE-4_PYQ.zip --apply --submit-for-review
```

The importer also accepts `SPRING_DATASOURCE_URL` (including the `jdbc:postgresql://` prefix). Never commit a database password or put it in this document. The importer requires Flyway V168, V177, V180, V196, V198 and V199; the assessment-only readiness function must validate the pack-to-test mapping and all 150 TRE 3.0 questions.

## What the script writes

The import is one PostgreSQL transaction. It idempotently creates/reuses the QuantaEdge-owned, classless `ASSESSMENT` course, ensures `ASSESSMENT_ONLY` delivery, and writes three versioned test packs. Each pack contains exactly one assessment for its paper, with ordered question snapshots and source hashes. Source package IDs and hashes are stable; repeat runs must match the existing package hash, pack identity and question count. The importer refuses to overwrite changed, archived or inconsistent pack records. It also creates audit rows for imported assessments and course lifecycle events.

The dry-run JSON reports the course type, delivery mode, hierarchy, each pack code/version and paper/question counts. A database apply additionally reports database IDs, the release state, and which packs/assessments were newly inserted.

## Where it appears after import

- **Admin Web — Content Studio / course selector:** the source-owned course is listed under QuantaEdge's institution once created; the imported tests can be inspected in the course-scoped assessment catalogue.
- **Institution Operations → Course Releases:** the source release is shown as `DRAFT` when imported without `--submit-for-review`.
- **HRMS Marketplace launch stepper — content-quality review:** with `--submit-for-review`, a structurally ready release is queued as `IN_QUALITY_REVIEW` for HRMS review.
- **Learner Marketplace:** not immediately. HRMS content-quality approval, QuantaEdge origin-institution approval, destination assignment when applicable, and HRMS offer approval/publication must complete first. Even then, each imported test stays learner-hidden until its questions/answers pass human review and its test publication gate passes.

## HRMS lifecycle and safeguards

`--submit-for-review` submits the structurally complete release into `IN_QUALITY_REVIEW`; it does **not** approve, make it shareable or publish any assessment. HRMS must approve the exact submitted fingerprint, then the QuantaEdge source-institution administrator approves the origin release. Only the resulting `SHAREABLE` release can be assigned through the HRMS-controlled distribution workflow. These are separate from question-answer review and student test publication.

The V199 readiness gate checks `ASSESSMENT` + `ASSESSMENT_ONLY`, the three expected versioned test packs, exact pack-to-assessment links, package hashes, question counts, and the rule that a published test cannot carry unresolved or unapproved answers. It does not rely on school-class, subject or chapter mapping. V196 includes the pack and pack-item rows in the canonical course fingerprint, preserving stale-release rejection if any content changes after submission.

## Validation

```powershell
python -m unittest discover -s tests -p test_import_tre4_course.py
```

The offline suite does not connect to PostgreSQL. The dry-run additionally validates the real source archive's hashes and exact question inventory. Before student delivery, review the original question wording, Hindi glyph fidelity, all options, topic metadata, the authoritative key and explanations; then publish through the supported human-review and release workflows.
