# Phase 1 — Existing Automated Test Evidence and Coverage Gaps

**Status:** Test-source review only. No test commands were executed by this audit pass.  
**Source baseline:** files present on `main` while Phase 1 documentation was being extended; confirm exact SHA/run before asserting current CI status.

## 1. How to read this document

A named test class proves that a test source exists, not that the current commit passed it or that an entire workflow is certified. The method names below show the intended assertion surface visible in test source. Tests can use mocks and therefore may not exercise database/provider/browser behavior. This document separates:

- **Source present:** test file and assertion intent found in repository.
- **Runtime executed:** test command was run and passed against an exact SHA.
- **End-to-end verified:** the real interface and connected services were exercised with a recorded environment and evidence.

In this Phase 1 audit, the items below have **source-present evidence only** unless a specific action/run is linked later.

## 3. Native Android test depth

The 15 JVM test files located under `apps/android/app/src/test` cover domain/UI contracts including navigation grouping, answers, lesson policy/recap/visual gates, math text, assessment timer, lesson classes, live player, QR verification, resource owner key, offline assessment sanitizer, recorded/offline video and tutor message parser. The `apps/android/app/src` directory currently contains `main` and `test`; no `androidTest` source directory was found in that tree.

Repository searches during this pass returned no matches for Playwright, Cypress, Puppeteer, WebdriverIO, `@playwright/test`, `createComposeRule`, `AndroidJUnit4`, Maestro or Appium. This is search evidence, not a mathematical proof that no external test harness exists outside the repository. The CI command found in `.github/workflows/ci.yml` is `gradle -p apps/android testDebugUnitTest assembleDebug`. This configures JVM unit tests and APK assembly; it is not a connected-device Compose interaction test. Do not represent the JVM suite as a complete emulator UI audit.

## 4. CI/static checks vs runtime tests

The inspected CI workflow includes:
- Route-inventory generator unit test and artifact generation.
- Localization catalog/static-copy checks for migrated routes and several Admin sections.
- Central branding/theme and structured-lesson UI contract scripts.
- Android UI localization/structured lesson contract checks and JVM unit tests plus APK build.
- API tests in a PostgreSQL-backed job and root Python content-import tests where change detection enables those jobs.
- Web, Admin and People build jobs (per change detection).

The inspected workflow does not show a comprehensive browser E2E suite that signs in as every persona and traverses the Web/Admin/People workflows. Build success, static string contract checks and unit tests cannot substitute for that suite.

## 5. Coverage gaps to drive next

1. Add/test a browser E2E harness for all three Web apps with isolated role/session fixtures and API/database reset strategy.
2. Add Android emulator/Compose interaction tests for high-risk user journeys, back/session restoration, compact displays, document/photo/QR pickers and offline/error handling.
3. Convert the 72-case scenario register into executable suites where possible; attach test IDs to reports and fail CI for critical authorization/tenant regressions.
4. Add specific data pack tests only after the installer/manifest is designed; test installation rollback, repeat install, cross-run isolation, interrupted uninstall and protected baseline preservation.
5. Link actual current-SHA CI runs and artifacts; keep all tests unexecuted until evidence exists.
6. For each scenario, link source test methods and mark coverage as direct, partial or missing after assertion review—not by class name alone.
