# QuantaEdge eight-layer textbook content pipeline

## Layer contracts

Every run is bound to a stable book ID and the SHA-256 of the exact complete-book PDF edition. A checkpoint from another edition is never silently reused. All generated assets are experimental review-only candidates; no stage publishes to student delivery.

1. Source visual inventory: every original PDF page, embedded-image occurrence and page preview with hashes and source-page linkage.
2. Exhaustive visual candidate preparation: eligible assets are represented; batch size is a checkpoint interval rather than a total candidate cap.
3. Review catalog and attachment manifests: source lineage and immutable bundle references.
4. Visual AI analysis: local Ollama processes embedded-image and page-preview rows with an explicit 8,192-token context, 1,024-token output ceiling and 360-second request timeout. Failed outputs remain resumable; an unsupported model visual label is conservatively mapped to `uncertain` with a human-review limitation rather than silently accepted.
5. Evidence/correction ledger: each page, text record, visual row, analysis and accepted correction is linked. Human corrections are sidecars; raw Layer 4 results remain unchanged.
6. Curriculum/concept map: the Layers 6–8 script maps every bounded segment to chapter/topic/microtopic/concept candidates, bilingual terms, objectives and source pages. Uncertain chapter IDs remain unresolved, not guessed.
7. Premium lesson generation: the same result produces a structured bilingual lesson candidate with explanation, a supported worked example when source permits, recap, paired objectives and 1–6 context-appropriate practice questions. The eight registered question types are a catalogue, not a required distribution: no one-of-each rule, no equal type counts and no padding. Questions choose their renderer contract from their actual response shape and link to exact supporting pages. Existing V3 image candidates are attached only when book ID, whole-book PDF hash, original source page and content-addressed display hash match. Image-observation questions must cite an allow-listed candidate attached to the same segment; they remain blocked until that exact visual is approved. Candidate images remain SOURCE_REFERENCE_ONLY, publication_allowed is false, and student_renderable is false.
8. AI tutor datasets: a deterministic page-level NCERT retrieval corpus is separate from conversational fine-tuning/SFT examples. SFT rows are deduplicated by stable IDs and grouped into non-overlapping train/validation/test splits. Neither dataset is automatically approved, fine-tuned or served.

## Native Ollama and model benchmark

The script scripts/quantaedge_layers_6_8.py uses Ollama's native /api/chat endpoint and JSON mode. The existing scripts/ai_training_dataset.py generator also defaults to native loopback Ollama. Local generation does not require an OpenAI API key. An API key is required only when an operator explicitly chooses the external OpenAI-compatible provider; that branch requires HTTPS and explicit confirmation of external processing.

The manual workflow .github/workflows/quantaedge-layers-6-8.yml defaults to benchmark-only. Benchmark output is bound to the current prompt, lesson-renderer contract and visual-candidate fingerprint. If the renderer schema changes without changing the prompt, `refresh-benchmark` revalidates saved raw outputs and rebuilds lesson previews with zero model calls; altered sample hashes or mismatched source segments are rejected. It compares qwen2.5:1.5b and qwen2.5:3b on the same two Class 6 NCERT Science (Curiosity) segments with the same prompt and source-bound Layer 5 evidence. Its committed report records JSON/schema validity, structured-lesson validity, page-citation validity and CPU runner latency. It intentionally leaves production_model null and production_model_selection PENDING_HUMAN_REVIEW; it never automatically selects a production model. A small sample is a screening benchmark, not proof of educational quality.

## Resource budget, persistence and resumability

- Do not run all 18 Class 6–8 subject/language whole books in one hosted runner job. Dispatch one exact source book ID per run.
- GitHub-hosted runners are CPU-only for this design; assume no GPU and bounded RAM, disk and runtime. The job has a 360-minute hard ceiling, supports at most 20 model calls per generation run and defaults to six. A lesson receives at most two hash-verified image-candidate links from segment source pages; absence of candidates does not invent a placeholder image. Benchmark runs test at most two excerpts per model and pull only the configured candidate models.
- Hosted runners are ephemeral: model weights may need to be downloaded again on every workflow invocation. Durable state is the source-bound Git checkpoint committed to main, not the runner's Ollama volume.
- Context and generation are bounded. Page text is split into lossless fragments, the segment builder checks that no source characters were dropped, and each Ollama call caps generation at 3,072 output tokens with an 8,192-token context ceiling. Benchmark excerpts are at most two pages / 5,000 characters; each report sample is capped at 100 KB JSON.
- JSON/JSONL writes use temporary files and atomic replacement. Successful segments are checkpointed after a small batch; resume skips successful records. Failed output is retryable. A PDF, extraction JSONL, Layer 5 ledger, model, benchmark report, segment/context budget or generation-configuration fingerprint mismatch fails closed rather than silently mixing incompatible work.
- Retrieval output has one row per original PDF page, including explicit non-retrievable rows for pages with no extractable text. Empty-text pages remain in `unresolved_text_pages` and cannot be counted as mapped even when they share a generation segment with readable pages. SFT output is separate from retrieval text, and source groups do not cross train/validation/test splits.
- Budget exhaustion is resumable IN_PROGRESS, not false completion. Even after machine checks pass, outputs stay DRAFT_REQUIRES_HUMAN_REVIEW and publication_allowed remains false.

## Recovering the existing Class 6 Curiosity Layer 5 checkpoint

The one-time workflow `.github/workflows/quantaedge-layers-1-5-resume.yml` is deliberately triggered by a separate marker-file commit under `.github/triggers/`. It retries the existing failed vision checkpoint using local `qwen2.5vl:3b` with an 8,192-token context, commits every small batch to `main`, and rebuilds the effective analysis plus actual Layer 5 ledger for the exact Curiosity PDF hash. It never writes `COMPLETE` itself: the ledger builder computes completeness from every page and eligible visual, and the workflow fails if any gap remains. A failed/incomplete run leaves its raw checkpoint and ledger committed for inspection/retry.

## Execution order

1. Run Layers 1–5 and verify the source's Layer 5 coverage ledger is COMPLETE for the exact whole-book PDF hash.
2. Dispatch the Layers 6–8 workflow in benchmark mode and review the committed comparison and sample output quality.
3. Decide the production model separately after checking Hindi fluency, factual/math correctness, answer keys, source linkage and practical latency. Run mode requires a successful benchmark sample and a separate explicit experimental-draft acknowledgement.
4. Use one book ID per run and repeat the same inputs until the per-book manifest has no pending segments. Review the map, lessons and both datasets; do not publish or fine-tune drafts.

## Correction overlay

The visual correction overlay remains at data/textbook-content-pipeline/class-N/books/BOOK_SLUG/visual-analysis-corrections.v1.json using schema quantaedge.visual-analysis-corrections.v1. Accepted entries require exact PDF/asset hashes, reviewer, reason and supported patch. Edition or asset mismatches fail closed, and raw visual analysis is not mutated.

## Direct local commands

From a clean clone on the machine that already runs Ollama, first ensure the source's Layer 5 coverage ledger is complete and the Ollama model is installed. The endpoint must be loopback (the script will refuse remote endpoints).

Benchmark sample candidates:
`python scripts/quantaedge_layers_6_8.py benchmark --repo-root . --source-book-id ncert-c6-english-fecu1 --endpoint http://127.0.0.1:11434 --models qwen2.5:1.5b,qwen2.5:3b --sample-segments 3 --output data/textbook-content-pipeline/model-benchmarks/class-6-ncert-curiosity.v1.json`

Resume a small review-only generation batch:
`python scripts/quantaedge_layers_6_8.py run --repo-root . --class-no 6 --source-book-id ncert-c6-english-fecu1 --endpoint http://127.0.0.1:11434 --model qwen2.5:1.5b --max-model-calls 6 --checkpoint-every 2 --allow-experimental-model --commit-checkpoints`

The same command can be repeated to resume. The model must first have a contract-valid sample in the committed benchmark report. Pick matching class and exact source-book ID for other tracks; do not reuse the Class 6 Science book ID for Class 7/8.

The existing general-purpose SFT generator is also Ollama-first:
`python scripts/ai_training_dataset.py generate --input-dir private-review --output data/ai-training/generated/drafts.jsonl --provider ollama --endpoint http://127.0.0.1:11434 --model qwen2.5:1.5b --target 25000 --batch-size 5 --max-api-calls 100 --generate`

## First bounded Class 6 generation run

The guarded Class 6 Curiosity pilot is an evidence-gated workflow chain. Commit `.github/triggers/layers1-5-class6-curiosity.trigger` to run `.github/workflows/quantaedge-layers-1-5-resume.yml`, which retries only missing/failed source-matched Layer 4 analyses and rebuilds the actual Layer 5 coverage ledger. After that workflow completes, `.github/workflows/benchmark-class6-curiosity-after-layer5.yml` verifies that the ledger is truly `COMPLETE` before it downloads Ollama, then benchmarks `qwen2.5:1.5b`, `qwen2.5:3b`, and `qwen3:4b` under the current prompt and renderer contract. The fresh report is committed under `data/`. If no candidate passes both schema and lesson-contract checks, generation remains blocked and the report is retained for diagnosis.

Only a successful fresh benchmark starts `.github/workflows/quantaedge-layers-6-8-generate-once.yml`. It rechecks the source, Layer 5 ledger, benchmark fingerprint, and production-selection safety, then chooses an eligible model only for a bounded experimental draft batch (six model calls). It does not set the production model, publish lessons, or approve content. Each model call is checkpointed to `data/`; an interrupted batch resumes from the durable matching segments. The run manifest remains `IN_PROGRESS` until the segment dataset is complete and valid.


### Context-driven practice and source coverage

Layers 6–8 no longer requires two MCQs per segment. The prompt permits 1–6 distinct questions chosen from the structured renderer catalogue according to the source, objective and learner task. The schema validator rejects unsupported types, invalid type-specific payloads, out-of-segment page citations and image-observation questions without an exact allow-listed embedded-image candidate. Changing the prompt/contract version invalidates older benchmark reports and checkpoints; run a fresh benchmark before model generation.

This per-segment generator is not a substitute for the structured chapter-authoring coverage ledger. For complete lessons, every inventoried section/subsection, figure/panel, table, activity, example, special note, keyword, summary item, end question and Learning further task must be mapped to a concrete lesson block/activity/question or an explicit review/exclusion disposition. Use `scripts/validate_structured_lesson_coverage.py`; count-only inventories cannot pass as item-level coverage. The question-type counts in reports are descriptive only.


## Canonical output path, application schema and DB response keys

Layers 6–8 first writes generated lesson candidates under its run output folder. These candidates are not discovered as lessons by the runtime API. The canonical application format is one UTF-8 JSON file per topic with schema_version equals quantaedge.structured-lesson.v1; artifact_type is a non-empty classification string (draft_lesson for generated drafts), saved under data/structured-lessons/class-{class}/{subject}/chapter-{NN}/topic-{NN}-{slug}.v1.json and registered in the matching production-index.v1.json.

Keep extra candidate metadata, but ensure the exact current keys exist: curriculum.class, curriculum.subject, chapter.chapter_number/title_by_locale, topic.topic_number/topic_id/title_by_locale, artifact_id, learning_objectives, source_refs, explain.blocks, practice.questions and workflow publication/review state. The API validates the chosen renderer contract and packages canonical JSON into the server JAR.

The DB does not persist the full lesson JSON. It keys question answers with artifact_id + artifact_sha256 + question_id; it keys activity responses with artifact_id + artifact_sha256 + block_id. artifact_sha256 is computed by the API over the exact final canonical JSON bytes; workflow.source_pdf_sha256 is a separate textbook-provenance hash. student_id comes from the authenticated request, never from model generation. Stable artifact IDs must fit varchar(120); question and block IDs must fit varchar(180).

After a human confirms the source/canonical chapter mapping, dry-run registration with scripts/register_structured_lesson_drafts.py and the target production index. The importer validates the precise source-book ID and whole-book PDF hash, preserves rich metadata and stable IDs, refuses overwrites, updates the index and never publishes. CI now validates the complete canonical index and all 39 existing topics against the application and DB-facing contracts.

Hash mismatch, missing page, duplicate asset ID, incomplete ledger or stale prompt/contract is a stop condition. Every generated artefact is review-only until a separate human approval and registration workflow completes.

### What is fixed in the Layer 5 bridge

Layers 6–8 now stop unless L5’s page text matches the extraction JSONL, its eligible visual rows match the Layer 1 inventory and Layer 4 raw output, the effective-analysis file points to the current raw-analysis SHA, and the exact source/ledger identities reconcile. For each segment, the prompt gets same-source, same-page visual summaries/concepts/visible text/limitations marked **unapproved**; output checkpoints, curriculum-map entries, lesson **generation_metadata**, SFT metadata rows, and run manifest preserve the ledger hash and IDs for audit. Benchmark validation checks the fixed Class 6 English Science anchor against its own current PDF, Layer 5 ledger and V3 candidate pack. A per-book generation run independently validates and fingerprints the target book’s own extraction, Layer 5 ledger and V3 candidates; the target is not incorrectly required to share the benchmark anchor’s book hash. This prevents the former gap where the ledger was merely used as a readiness flag/fingerprint and its visual-analysis content never reached lesson generation.

The exact visual crosswalk now ties every V3 embedded-image candidate to Layer 1/Layer 5 occurrence asset IDs and the same source-image SHA-256. Visual-question generation uses only that image’s matching Layer 5 analysis; page overlap alone cannot attach an unrelated analysis. Candidate visual blocks remain non-publishable and non-student-renderable.

This changes the prompt and lesson provenance contract, so prompt/lesson-contract versions are bumped. Old run directories are retained; new runs use the **-v5** directory rather than mixing old checkpoint content with the stricter same-asset crosswalk. The benchmark anchor must be rerun because reports with the older prompt are intentionally rejected.

### Validation status vs. end-to-end execution

The package-name expansion fix and the new contract/test code are committed to **main**; push-triggered validation can confirm Python/unit-test contracts. That is not evidence that a full live Layer 1–8 run has completed. The reported Class 6 run stopped at the Layer 1–3 / Layer 4 handoff before Layer 4–5 execution, so it does not prove a new effective analysis/coverage ledger exists for that run, and no new Layers 6–8 artifacts should be claimed as generated from it. A fresh **analyze_all** run must produce a new complete L5 ledger first; then run the benchmark for the updated prompt and finally the bounded per-book generation.


### Git storage invariant

All generated textbook pipeline data committed to Git lives under `data/`: source extractions, visual inventories/candidates/catalogs, Layer 4–5 evidence and coverage ledgers, Layer 6–8 checkpoints/maps/lesson candidates, retrieval datasets and SFT candidates. The Admin Content Studio reads review-only visual catalogs from `data/textbook-visual-candidates-v3/catalogs/` and its index from `data/textbook-visual-candidates-v3/index.v1.json`; generated review data is not duplicated under `apps/*/public/`. Checkpoint helpers reject commit targets outside `data/`, and `scripts/validate_pipeline_data_locations.py` scans repository paths before candidate/analysis/generation checkpoints are committed.


## Recovery contract and UI resume modes

The GitHub Actions UI exposes different actions for starting work and recovering work. A push-triggered validation run is not a content-processing run. Use **Actions → Prepare textbook visual candidates v3 → Run workflow** for Layers 1–5, or **Actions → QuantaEdge Layers 6–8 - local Ollama pipeline → Run workflow** for generation.

### Layers 1–5 UI choices

- **prepare_only** — resolve the selected whole-book sources, restore or build each book's fingerprinted candidate bundle, persist indexes/catalogs, and stop before vision analysis.
- **analyze_all** — ensure the complete candidate set exists by restoring matching per-book bundles or building only missing/stale books, then continue through Layers 4–5. Matching successful asset analyses are reused.
- **resume_preparation** — resume a cancelled Layers 1–3 batch. For each whole book, validate inputs and reconstruct its Layer 1 inventory, then restore the matching deterministic candidate-pack tag if present. It rebuilds only a missing/invalidated book, publishes that book's immutable GHCR bundle immediately, and only then moves to the next book. The final Git metadata/catalog commit can happen after the batch: completed books survive cancellation in GHCR and are recovered on the next run.
- **resume_layers_4_5** — do not rebuild candidate packs, contact sheets, lesson-attachment catalogs, or candidate GHCR bundles. Validate the selected source IDs, exact source PDF hashes, committed extraction manifests and candidate-pack fingerprints. For every book, restore its previous immutable Layer 1 inventory bundle using the tag and SHA-256 in `data/textbook-visuals/{book_slug}/visual-pipeline-index.v1.json`. A bundle is reused only after archive SHA, paths, source identity, inventory schema, stable asset IDs, asset hashes and current page-text hashes validate. If the referenced inventory bundle is genuinely missing (registry 404), Layer 1 may be rebuilt only if the regenerated inventory matches the committed inventory byte-for-byte; a corrupt bundle, non-404 registry error, changed text context, mismatched source edition, or missing/stale candidate pack stops before model inference. Then restore/reuse the matching Layer 4 checkpoint from Git or ORAS, process only unfinished/failed/stale-context assets, and recompute Layer 5 from verified raw analysis plus the current correction overlay. The `checkpoint_batch_size` UI setting controls how many assets are processed before durable Git/GHCR savepoints: choose `1` for the smallest possible uncheckpointed window, or a larger value to reduce commit/registry overhead.

The vision model name is part of checkpoint identity. A resume request must not silently turn into a different-model full rerun. If the selected model has no checkpoint while a prior Layer 4 run is recorded for that book, the preflight fails with an explanation; choose **analyze_all** only when deliberately beginning a different model/configuration run. The inventory's per-page text hashes are also compared with the current extraction JSONL; a same-PDF but revised extraction is not allowed to reuse old visual interpretations as though their model context were unchanged. Layer 5 explicitly marks stale-context checkpoints incomplete, and Layers 6–8 refuse to consume those ledgers.

### Dedicated recovery UI entrypoints

The Actions list also exposes fixed-mode launchers for [Layers 1–3](https://github.com/Manav326/QuantaEdge/actions/workflows/resume-textbook-visual-layers-1-3.yml), [Layers 4–5](https://github.com/Manav326/QuantaEdge/actions/workflows/resume-textbook-visual-layers-4-5.yml), and [Layers 6–8](https://github.com/Manav326/QuantaEdge/actions/workflows/resume-quantaedge-layers-6-8.yml). They delegate to these shared workflows; they do not clone the execution steps or change the checkpoint contract. Pick the layer range where the interruption occurred, then preserve the exact class/book/edition/model/configuration from the prior attempt. For Layers 4–5, the launcher fixes the mode to `resume_layers_4_5`; for Layers 6–8, it fixes `mode=resume` and retains strict existing-checkpoint preflight.

### Layers 6–8 UI choices

- **benchmark** — benchmark only; this benchmark is intentionally anchored to Class 6 English Science (Curiosity).
- **run** — start a bounded, review-only draft run. When a matching checkpoint already exists, completed segments are reused automatically.
- **resume** — require an existing checkpoint with a matching input fingerprint. Preflight runs before Ollama startup or model download and checks the source edition/text, Layer 5 ledger, V3 visual-candidate fingerprint, model, benchmark report, prompt version, renderer contract, segmenting options and existing checkpoint schema. Missing/mismatched checkpoints fail safely instead of starting work from zero. Retryable segments are attempted up to the new invocation's `max_model_calls`; completed and terminal `UNRESOLVED_SOURCE_TEXT` segments are not re-generated. If no model calls remain, the workflow rebuilds aggregate review outputs from the durable checkpoint and skips Ollama startup, model download and inference entirely. The `checkpoint_every` UI setting controls the number of model calls between Git savepoints; use `1` for the safest recovery point or a larger value to reduce commit overhead.

For any resume, keep the class, exact whole-book ID, model and generation settings the same. Reusing a checkpoint after the edition, text, prompt, contract, benchmark, visual evidence or relevant configuration changes is not safe; the pipeline refuses to mix the incompatible records. Select a deliberate fresh-run path and a new versioned checkpoint namespace after reviewing the cause rather than deleting or overwriting the old checkpoint.

### Checkpoint / interruption decision table

| Situation | Required behaviour |
| --- | --- |
| Cancelled during Layers 1–3 candidate generation | Choose **resume_preparation**. It restores each exact fingerprinted per-book GHCR bundle and only rebuilds books whose matching checkpoint is genuinely missing. A per-book bundle is pushed before the next book begins, so a later Git catalog commit is not required to recover completed preparation work. |
| Cancelled after Layers 4–5 started for a book | Restore that book's verified inventory bundle and raw analysis checkpoint; reuse successful asset results and process only missing/failed/stale-context assets. |
| One or more model calls failed | Preserve explicit error rows. A later invocation with the same fingerprint retries those rows; don't retry them repeatedly within the same batch/run. |
| Input source PDF / edition differs | Fail closed. Never join analysis from different PDF hashes into one ledger. |
| Model or prompt differs | Do not silently call it a resume. Require an explicit new analysis run/checkpoint identity. |
| Correction overlay changes | Rebuild Layer 5 effective analysis/coverage from the preserved raw Layer 4 result. Do not spend vision-model calls to apply a reviewer correction. |
| Layers 6–8 interrupted mid-generation | Commit checkpoints under `data/`; reuse completed segment results; retry only errors/pending segments on resume. |
| All Layers 6–8 segments are already terminal but aggregate files are stale/missing | Rebuild the map, lesson candidates and datasets from checkpointed rows with zero model calls and no model download. |
| Checkpoint or artifact is corrupt, contradictory, or unverifiable | Stop before expensive model work. Keep existing evidence untouched and report the invalid fingerprint/hash rather than pretending the stage resumed. |

### Operational signals

Successful recovery logs should distinguish `REUSED_FROM_GIT`, `RESTORED_FROM_GHCR`, `BUILT_AND_PUBLISHED`, `RESTORED_LEGACY_GHCR_BUNDLE`, `INVENTORY_BUNDLE_REUSED`, `INVENTORY_BUNDLE_PUBLISHED`, `BATCH_CHECKPOINTED` and `OUTPUTS_REBUILT_WITHOUT_MODEL_CALLS`. `IN_PROGRESS` is not completion. The coverage ledger determines Layer 5 completion; the saved segment statuses plus input fingerprint determine Layers 6–8 completion. All generated textbook artifacts stay review-only, and all committed generated data remains under `data/`.
